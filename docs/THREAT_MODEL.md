# Threat model

What the guard protects against, what it deliberately leaves out for a hackathon demo, and what production would add.

## Assets

- The owner's money: the PayPal mandate (vault id) and the ability to charge it.
- The PayPal sandbox credentials in `.env`.
- The integrity of decisions: a request must never be paid unless the owner's rules (and, from M3, the AI reviewer) allowed it or the owner approved it.

## Trust boundaries

| Component | Trusts | Holds |
| --- | --- | --- |
| Shopping agent (LLM or mock) | nothing it reads on the web | no credential, no token, no database. Only MCP tool results: the request's own fields, its status, reasons, flags, the reviewer's sentence and PayPal object ids |
| MCP server (`src/mcp`) | the guard's JSON API | no credential of its own: it does not load `.env` and is started without PayPal variables in its environment; tool results carry no credential, token or vault id |
| Guard server (`src/server`, `src/guard`) | its database and the owner | `.env` (sandbox credentials), the database with the vault id |
| AI reviewer (`src/review`) | nothing it reads: the request, the page and the history are data | the LLM key in anthropic mode (handed to the provider, registered with the redactor); it returns a schema-bound verdict that code can only tighten |
| Synthetic shop (`src/shop`) | nothing; it is the hostile party in the demo | static pages, no scripts, strict CSP, own origin |

## Threats covered

- **Prompt injection through product pages.** Merchant text is data. The deterministic engine never reads it as instructions; the dashboard escapes every request field (tested with script, event-handler and `javascript:` payloads); the shop runs on a separate origin from the dashboard. The reviewer reads the page the agent read, hidden text included, flags instructions aimed at agents (`PROMPT_INJECTION_SUSPECTED`) and reasons that claim an approval the agent cannot have (`CLAIMS_OWNER_APPROVAL`), and can only tighten a decision; in anthropic mode the page goes to the model inside tags marked as untrusted, with angle brackets neutralised so it cannot close a section (tested).
- **An agent spending beyond its rules.** Caps, monthly budget, allowlists and hours are enforced before any PayPal call and checked again after the review, with the rules, budget and clock of that moment; the AI reviewer cannot loosen them; an LLM failure, refusal, timeout or unusable answer means at least HOLD (tested against a fake provider).
- **Budget races.** Requests submitted together are counted against each other first come first served while they are under review, so they cannot all pass a budget that fits only one; the second evaluation after the review also sees a sibling that was decided first (D16, tested).
- **The reviewer fetching agent-supplied URLs (server-side request forgery).** `source_url` comes from the agent, and the guard fetches it to see what the agent saw. The fetch is fenced (`src/review/page.ts`, tested): http(s) only, origin on an allowlist (the synthetic shop by default, `REVIEW_PAGE_ORIGINS` adds more), redirects never followed, 256 KB and 3 s caps, HTML only. A URL outside the allowlist is not requested at all; the request is reviewed without the page and carries `PAGE_UNAVAILABLE`.
- **Credential leakage.** Secrets live only in `.env`; the client redacts bearer, basic-auth and configured values from every field of every error, before truncating, and turns connection, read and parse failures into fixed text; the executor registers the vault id with the redactor before each call; audit details carry PayPal object ids (setup token ids masked), the guard's ids, amounts, statuses and owner notes, never a token (tested); the dashboard shows PayPal failures as status, error name, issue codes and debug id, never a response body; the LLM key is read once, handed to the provider and registered with the redactor, and provider error bodies are never stored or shown: known failures are classified into fixed phrases and any other is redacted and clipped (tested with a 401 whose body contains the key); database and state files are gitignored and refused by the pre-commit hook; gitleaks runs in CI.
- **Double charging, and the opposite.** Every create, capture and refund carries a `PayPal-Request-Id` derived from the request id; a crash between steps is resumed by looking up the recorded order instead of re-creating it, and an error during that lookup, a 4xx included, is an unknown outcome, never a refusal. An outcome PayPal never confirmed (no connection, an unreadable answer, a 5xx, a 401/403/408/429, a `PENDING` capture) is left open rather than booked as failed: the amount stays counted and the owner's retry replays the same keys to find out what happened (D16, D17, tested). An agent that got no answer repeats `request_purchase` with the same `intent_id` and gets the request it already made, never a second charge; the same id with a different purchase is refused (D17, tested).
- **A restart during a review.** A request the previous process left `EVALUATING` is decided at the next start with the rules of that moment and no model call: held for the owner (blocked when the rules say so), never charged, so it neither hangs nor keeps counting against the requests that follow (D17, tested).
- **Cross-site control of the login-less dashboard.** A web page open in the owner's browser could otherwise post the dashboard's forms (approve, refund, change the rules) or JSON requests to 127.0.0.1, embed the dashboard in a frame, or reach it through a rebound DNS name. The guard checks the `Host` header against localhost and `PUBLIC_BASE_URL`, refuses a form-typed POST unless its `Origin` or `Sec-Fetch-Site` is same-origin (hono/csrf), sends `frame-ancestors 'none'` and `X-Frame-Options: DENY`, and takes agent requests as `application/json` only (D16, tested). What this does not add is a login: a process on the same machine can call every route.
- **Live money.** The sandbox host is hard-coded; the process refuses to start when `PAYPAL_ENV` is anything but `SANDBOX`; the client never follows a redirect.

## Out of scope for the demo (and what production would add)

- **No authentication on the dashboard or the agent API.** Any process on the machine (or on the Wi-Fi, with `HOST=0.0.0.0`) can submit requests as any agent, approve a held one or change the rules; the cross-site protections above stop web pages in the owner's browser, not local processes. The server binds to `127.0.0.1` by default; `HOST=0.0.0.0` is for showing the dashboard on a phone on the same Wi-Fi during the demo, with `PUBLIC_BASE_URL` set to that address. Production: owner login with a second factor, per-agent API keys or mTLS for the MCP server, rate limits and a request body cap.
- **No webhooks.** Settlement is read from the synchronous API responses; an answer that never arrives keeps the payment open for the owner's retry (D16), and a refund PayPal answers `PENDING` stays `REFUND_PENDING`, counted against the budget, until the owner's **Check refund** finds it completed or cancelled (D17). Production: `PAYMENT.CAPTURE.COMPLETED` / `REFUNDED` webhooks with signature verification, and reconciliation instead of a button.
- **One owner, one mandate.** The database holds the single active mandate; a multi-tenant deployment would scope mandates, agents and policies per owner and encrypt the vault id at rest.
- **The model reads hostile text.** A page could be written to talk the model into a lower risk. That is why the deterministic checks are a floor the model cannot lower, the risk-to-decision mapping lives in code, and the model's only outputs are an enum, a list from a fixed vocabulary, a boolean and two sentences. Production would add a second, cheaper classifier on the page text alone and evaluation sets of hostile pages.
- **A review takes time.** While it runs the request is `EVALUATING`. Since D16 its older siblings count against it and the rules run again when the review ends, so simultaneous requests cannot all pass a budget that fits only one; what remains is that an owner approving a held request can knowingly exceed the budget and the other soft rules (D10), while the hard ones (a disabled agent, the hard ceiling, a missing policy, the currency) are checked again at approval and refuse it (D17), and that the heuristics can be phrased around (a line break inside "approved by owner", zero-width or full-width characters), which the amount and merchant rules still catch.
- **Synthetic everything.** No real merchant receives money (DECISIONS D3): the guard is a wallet operator that charges the owner's PayPal into its own sandbox business account.
